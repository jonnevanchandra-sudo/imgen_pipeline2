When the client has responded to the Visual Discovery Package (Stage 1.5) and their picks have been codified by Stage 5.5, the `ClientPreferenceContract` is available as input to this stage.

When present, the ClientPreferenceContract informs **flexible attribute decisions** within PreservationContracts. It does NOT:
- Override immutable attributes — preservation of uploaded assets and named products is unchanged
- Override brand or strategic direction

# Purpose

Scene Assembly transforms visual interpretation into a spatially coherent scene blueprint consumed by downstream systems.

Scene Assembly should maximize reuse of existing scene truth before generating new elements.

Preservation takes precedence over recreation and overrides downstream convenience.

Uploaded assets are source truth.

Scene Assembly determines:
- asset extraction and classification (from uploaded reference images)
- asset preservation
- scene relationships
- spatial coherence
- environmental continuity
- generation requirements
- scene realization logic

Scene Assembly should NOT:
- replace preserved identities
- constrain downstream visual flexibility

## From Uploaded Reference Images (optional)
Any image files provided alongside this stage. These may include:
- brand logos
- product photography
- identity-bearing assets (faces, people)
- environmental references

If reference images are provided, run the **Reference Asset Extraction Block** before scene construction.
If no reference images are provided, skip that block entirely.

## From Stage 5.5 — ClientPreferenceContract (optional, NEW in v5.2.5)

If a `ClientPreferenceContract` is available from Stage 5.5, consume it here.

**How to use it:**

The ClientPreferenceContract informs flexible attribute decisions only. Apply it in this order:

1. **Selected signals → resolve flexible attributes toward**
   For each PreservationContract where a flexible attribute has multiple valid options, prefer the option that aligns with the client's `extracted_signals` (lighting, color_palette, subject_scale, emotional_tone, genre).
   
   Example: If `lighting: "warm amber city ambient"` and an entity's flexible attributes include lighting, prefer warm-ambient approaches over cool/neutral ones.

2. **Avoidance signals → resolve flexible attributes away from**
   For each avoidance signal in `ClientPreferenceContract.rejected`, treat it as a soft constraint on flexible attributes.
   
   Example: If avoidance_signal is `"avoid cold blue-dominant lighting"`, prefer warmer lighting options in flexible attribute decisions.

3. **Immutable attributes are not affected** — client preferences cannot override any immutable attribute from the Reference Asset Extraction Block, ProductSpec, or any Critical/High preservation priority.

4. **Conflicts pass through** — if a client signal conflicts with an immutable attribute or upstream brand direction, note it in the SceneContract as `ClientPreferenceConflict` (see output schema addition below). Do not resolve it here — that belongs to Stage 7 (Synthesis).

5. **If `aesthetic_confidence: Low`** — apply client signals as weak hints only. Do not let low-confidence preferences override scene construction logic.

# Reference Asset Extraction Block

**Activate when:** One or more reference images are uploaded alongside this stage.
**Skip when:** No reference images are provided.

## Step 1 — Read the image

For each uploaded reference image:
- Observe what is visually present: shapes, letterforms, colors, icons, proportions, structural elements
- Do not infer from training data — describe only what is directly observable in the image
- Note anything that must survive exactly in the generated output

## Step 2 — Classify the asset

Assign one or more functional roles (see Asset Classification section):
- **Brand-Bearing** — contains a logo, wordmark, or brand mark that must survive exactly
- **Identity-Bearing** — contains a person or face whose identity must survive
- **Environmental** — contains a space or setting to be reproduced
- Other roles as applicable

## Step 3 — Assign IDs

For each reference image:
- Assign an `asset_id` (e.g. `asset_01`, `asset_02`)
- Assign an `entity_id` that maps this asset to its role in the scene
- Assign a `prompt_reference_id` (e.g. `reference_asset_01`) — this is the identifier the Prompt Compiler will use in the BRAND_ASSETS block to tell the image generator which attached file to look at

## Step 4 — Extract immutable attributes

List only directly observed attributes. These become the immutable attributes in the PreservationContract for this entity.

Examples for a brand logo:
- Wordmark text and typeface style
- Any icon or symbol replacing or accompanying the wordmark
- Tagline text if present
- Color of logo elements
- Overall proportional format (horizontal, stacked, etc.)

## Step 5 — Note flexible attributes

List attributes from the reference image that should NOT be locked into the scene:
- Background color / isolated color field (logo will appear on a different surface in the scene)
- Exact scale (will adapt to scene composition)
- Exact placement (will adapt to scene layout)

## Step 6 — Set generation rule

Mark the entity source as `"Reference Asset"` in the SceneContract.

Generation rule: `"Reproduce from [prompt_reference_id] — do not generate from training data."`

This rule must travel through Synthesis unchanged and reach the Prompt Compiler.

## Step 7 — Build ReferenceAssetManifest entry

For each reference-locked entity, create a manifest entry (see Output Schema). This is app-level metadata — it lists which files the app must attach to the image generation API call. It is NOT sent as text to the image generator.

# Asset Preservation System

## Purpose

Preserve uploaded asset recognizability while allowing scene adaptation.

Preservation defines what may change and what must remain stable.

Generated elements should adapt around preserved identities.

## Dynamic Identity Preservation Profiles

The system should infer:
- preservation priority
- recognizability requirements
- immutable attributes
- flexible attributes

---

## Preservation Priority

Critical | High | Medium | Flexible

Priority Order:
1. User Constraints
2. Critical Identity Systems
3. Core Brand Systems
4. Environmental Systems
5. Generation Flexibility

## Immutable Properties
What are recognizability-defining attributes?

Example:
- facial structure
- silhouette
- logo geometry
- architectural identity
- color system
- typography identity
- product shape

## Flexible Properties
What are adaptable attributes?

Example:
- pose
- perspective
- lighting
- environment
- positioning
- scale adaptation

## Recognizability Requirement

**Near Exact:** Identity-defining properties should remain almost unchanged. Only minimal adaptation acceptable for perspective integration, scale adjustment, environmental positioning, lighting adaptation.

**Strong Match:** Core identity-defining properties must remain stable. Limited adaptation acceptable as long as the entity remains clearly recognizable.

**Approximate Match:** Primary recognizability cues should remain stable, but moderate structural adaptation is acceptable.

**Loose Match:** Only broad recognizability continuity required. Significant adaptation acceptable.

## Example: Specific Product Model (from v5.1)

**Trigger:** CampaignContract `MandatoryRequirements.ProductSpec` contains a named product model entry.

**Rule:** A named product model must be locked as a named entity with both its model identifier AND its key visual descriptors. Do not rely on the model name alone — include the visual descriptor summary from `ProductSpec.key_visual_identifiers` directly in the PreservationContract immutable attributes.

**Why:** Image generators may not have accurate training data for a specific product model. "Nike Pegasus 41" alone can produce a generic shoe. The visual descriptors are the actual instruction the generator reads; the name is the anchor that links them.

Preservation Priority: Critical
Recognizability Requirement: Near Exact
Source: Generated (no reference image needed — descriptors come from CampaignContract)

Immutable Attributes:
- product model name — stated explicitly (e.g. "Nike Pegasus 41")
- sole profile (from `ProductSpec.key_visual_identifiers`)
- upper construction
- overall silhouette
- brand mark geometry
- colorway — only if mandated in `ProductSpec.colorway`; omit if flexible

Flexible Attributes:
- lighting on the shoe surface
- exact rotation / viewing angle
- scale
- lace color (if not mandated in colorway)
- degree of wear / newness

**Downstream flow:** Both the model name and visual descriptor summary must flow through Synthesis and reach the Prompt Compiler's `brand` key in HIGH. The Prompt Compiler must write them together — model name first, visual identifiers following.

## Example: Reference Asset — Brand Logo (from v5.2)

**Trigger:** A brand logo or wordmark image was uploaded as a reference asset.

**Rule:** Immutable attributes must come from direct observation of the uploaded image — not from training data or inference. The `prompt_reference_id` assigned here must be used in the Prompt Compiler's BRAND_ASSETS block verbatim.

Preservation Priority: High
Recognizability Requirement: Exact Match
Source: Reference Asset

Immutable Attributes (observed from image — examples):
- wordmark text and letterform style
- any icon replacing or accompanying the wordmark (describe shape, position, relationship to letterforms)
- tagline text if present
- color of all logo elements
- horizontal/stacked/proportional format

Flexible Attributes:
- background color from reference image (logo will appear on a venue surface or banner, not the original background)
- scale relative to scene
- exact placement in scene
- bokeh rendering depth (may be soft but must remain legible)

**Generation rule:** `"Reproduce from [prompt_reference_id] — do not generate from training data."`

**Downstream flow:** The `prompt_reference_id` must reach the Prompt Compiler unchanged. The Prompt Compiler will:
1. Include a BRAND_ASSETS block in VisualPrompt referencing this ID with a reproduction instruction
2. Include a ReferenceAssetManifest entry listing the file for API attachment

This is the mechanism by which the image generator sees the reference image again at generation time.

# Physical Construction System

## Purpose

Construct coherent scene structures.

Scene Assembly is responsible for:
- scale coherence
- perspective continuity
- spatial continuity
- environmental continuity
- physical coherence

Scene Assembly preserves:
- scene coherence
- spatial relationships
- environmental compatibility

NOT:
- visual styling
- rendering aesthetics
- cinematic framing
- lighting aesthetics
- composition aesthetics

---

## Reality Model

Defines the coherence rules used for scene construction and validation.

Possible reality models:
- Realistic
- Stylized
- Cinematic
- Symbolic
- Surreal
- Abstract

The objective is not physical realism. The objective is reality-model coherence.

---

## Physical Inference Priority

1. Explicit user constraints
2. Uploaded asset analysis
3. Contextual model inference

Model inference should only occur when higher-confidence information is unavailable.

- perspective relationships
- environmental continuity
- physical anchoring

- environmental integration

## Preservation Validation

Validate:
- required assets retained
- immutable attributes preserved
- recognizability requirements maintained
- preservation priorities respected
- flexible attributes remain within allowed adaptation range
- preservation contracts contain no violations
- every Reference Asset entity has a `prompt_reference_id` assigned
- every Reference Asset entity has a corresponding entry in `ReferenceAssetManifest`

---

## Physical Validation

Validate:
- scale relationships comply with declared scale rules
- perspective relationships comply with declared perspective rules
- anchoring relationships comply with declared anchoring rules
- environmental relationships comply with declared environmental behavior rules
- scene relationships remain internally consistent
- no unresolved spatial contradictions remain
- no unresolved environmental contradictions remain

In all reality models:
- preservation contracts remain satisfied
- immutable attributes remain unobstructed by conflicting scene elements

# Downstream Handoff Rules

## For Reference Asset entities

Every entity with `source: "Reference Asset"` must carry its `prompt_reference_id` through all downstream stages unchanged.

Synthesis must NOT strip, rename, or compress `prompt_reference_id` values.

The Prompt Compiler (Stage 8.2) must:
1. Include a `BRAND_ASSETS` block in VisualPrompt for each reference-locked entity — using the `prompt_reference_id` as the reference handle and including a reproduction instruction derived from the immutable attributes
2. Include the `ReferenceAssetManifest` as a sibling key to VisualPrompt in the output JSON

This is how the image generator is shown the reference image at generation time — the BRAND_ASSETS instruction names the file by ID, and the ReferenceAssetManifest tells the app which file to attach.

## For named product model entities

Both the model name and visual descriptor summary must travel through Synthesis and reach the Prompt Compiler's `brand` key in HIGH.

The Prompt Compiler must write them together — model name first, visual identifiers following.

## For ClientPreferenceContract

If `aesthetic_confidence: High` and the client's avoidance signals are unambiguous, pass them through Synthesis into the Prompt Compiler's NEGATIVE block.

`ClientPreferenceConflicts` must travel to Stage 7 (Synthesis) for resolution.
