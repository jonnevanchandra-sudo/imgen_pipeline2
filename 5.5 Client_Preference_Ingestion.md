# Client Preference Ingestion Framework
Version: 1.0
Stage: 5.5 — Client Preference Codification
Position: After Stage 4 (Art Direction), before Stage 5.2.5 (Scene Assembly)

---

## Purpose

Stage 5.5 receives the client's visual preference picks from Stage 1.5 and translates them into a structured `ClientPreferenceContract` for consumption by Scene Assembly (Stage 5.2.5).

**This stage only codifies what the client said.** It does NOT:
- Make creative decisions
- Override brand or strategic direction
- Interpret the client's language beyond what they stated

If the client's picks conflict with upstream brand/strategic direction, Stage 5.5 flags the conflict in `ClientConfirmationRequired` and passes it downstream. Resolution belongs to Stage 7 (Synthesis).

**If no client picks are available** (client did not respond before this stage runs), Stage 5.5 is skipped entirely. Stage 5.2.5 runs without a ClientPreferenceContract — identical behavior to Stage 5.2.

---

## Decision Architecture

| Layer | Decision Type |
|---|---|
| Art Direction | Visual Interpretation |
| **Client Preference Ingestion** | **Client Signal Codification** |
| Scene Assembly (5.2.5) | Scene Construction + Client Preferences |

---

## Inputs

### From Stage 1.5
- `VisualDiscoveryPackage.archetypes` — the reference options shown to the client (needed to look up archetype details from the client's stated picks)

### From Client Response (provided by app)
- Which archetype IDs the client selected
- The client's stated reasons for each selection (their words — preserve exactly)
- Which archetype IDs the client rejected (if stated)
- The client's stated reasons for rejecting (their words — preserve exactly)
- Any additional images or references the client provided themselves
- Any free-text preference statement from the client

---

## Processing

### Step 1 — Match client picks to archetypes

For each selected archetype ID, look up the full archetype entry from the VisualDiscoveryPackage.

### Step 2 — Extract signals from selected archetypes

For each selected archetype, extract aesthetic signals from the archetype's `visual_description`, `emotional_tone`, and `genre_reference`. Map them to the signal fields below. If a field cannot be inferred from the archetype or the client's stated reason, set to `null`.

Signal fields:
- `lighting` — inferred lighting quality (e.g. "warm amber city ambient", "high key diffused")
- `color_palette` — dominant color register (e.g. "warm amber + cool blue", "desaturated muted tones")
- `subject_scale` — how subjects are framed (e.g. "full body", "tight portrait", "environmental scale")
- `emotional_tone` — the emotional register the client responded to
- `genre` — the photography/advertising genre the client leaned toward

### Step 3 — Extract avoidance signals from rejections

For each rejected archetype, extract what the client was pushing away. State as a concrete avoidance signal (e.g. "avoid cold blue-dominant lighting", "avoid high-fashion editorial staging").

### Step 4 — Write client_preference_statement

Synthesize a single plain-language statement of the client's overall aesthetic direction from their picks, rejections, and any free-text they provided. Use their words where possible.

### Step 5 — Set aesthetic_confidence

| Level | Condition |
|---|---|
| `High` | Client selected 2+ archetypes with clear stated reasons; rejections are specific |
| `Medium` | Client selected archetypes but reasons are vague; or only 1 selection made |
| `Low` | Client responded but signals are ambiguous or contradictory |

### Step 6 — Flag conflicts

If any selected archetype signal conflicts with upstream brand/strategic direction (e.g. client selected "cold minimal" but BrandContract locks warm-tone identity), flag it in `ClientConfirmationRequired`.

## Output: `ClientPreferenceContract`

```json
{
  "ClientPreferenceContract": {
    "metadata": {
      "brand": "string",
      "campaign": "string",
      "framework": "Client Preference Ingestion v1.0",
      "stage": "5.5"
    },
    "selected": [
      {
        "archetype_id": "ref_B",
        "archetype_name": "string",
        "user_reason": "string — client's exact words where possible",
        "extracted_signals": {
          "lighting": "string or null",
          "color_palette": "string or null",
          "subject_scale": "string or null",
          "emotional_tone": "string or null",
          "genre": "string or null"
        }
      }
    ],
    "rejected": [
      {
        "archetype_id": "ref_D",
        "archetype_name": "string",
        "user_reason": "string or null",
        "avoidance_signal": "string — what to avoid in scene construction"
      }
    ],
    "client_preference_statement": "string",
    "aesthetic_confidence": "High | Medium | Low",
    "ClientConfirmationRequired": [
      {
        "conflict": "string — what signal conflicts with what upstream direction",
        "client_signal": "string",
        "upstream_constraint": "string",
        "resolution": "Deferred to Synthesis"
      }
    ]
  }
}
```

`ClientConfirmationRequired` is omitted if no conflicts exist.

---

## Downstream Handoff

The `ClientPreferenceContract` is passed as optional input to Stage 5.2.5 (Scene Assembly).

Stage 5.2.5 uses it to inform flexible attribute decisions within PreservationContracts:
- Selected signals inform which flexible attributes to resolve toward
- Avoidance signals inform flexible attributes to resolve away from
- If `aesthetic_confidence: High`, avoidance signals may flow through Synthesis into the Prompt Compiler's NEGATIVE block

Stage 7 (Synthesis) resolves any `ClientConfirmationRequired` conflicts — it has full authority to weigh client preference against brand/strategic direction.

---

## Success Criteria

✓ Every selected archetype has extracted_signals populated (null where genuinely uninferable — not left blank)

✓ `client_preference_statement` uses the client's own words where possible

✓ `aesthetic_confidence` is set with a stated reason

✓ Conflicts with upstream direction are flagged, not silently resolved

✓ No new creative decisions introduced — only client signals codified
